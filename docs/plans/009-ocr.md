# Plan 009 - OCR of operator-taken screenshots

Status: done (2026-10-05); refute rounds 2/3 PASS. Lanes: `build` (slice A), `data` (slice B).

## Engine (adjudicated 2026-10-04)

Decision: Windows built-in `Windows.Media.Ocr` (WinRT), driven by a vendored
PowerShell 5.1 script `tools/ocr.ps1` run with `powershell.exe -NoProfile
-NonInteractive` and CREATE_NO_WINDOW, one image per call, JSON lines out
(`{text, lines: [{text, x, y, w, h}]}`). Alternatives: Tesseract (an install
plus a language pack; breaks stdlib-only), a cloud OCR API (sends the
operator's screenshots off the box; needs a key), Python packages (breaks
stdlib-only). Why: ships with Windows 10, offline, no install, no key.
Reverses if: accuracy on BDO's UI font is measured below usefulness (silver
digits misread in more than 1 of 10 operator screenshots), then Tesseract is
re-adjudicated. The `_example_ocr_key` secret reference stays unused.

## Slice A - server (lane `build`)

`server/ew/ocr.py` + `tools/ocr.ps1` (ASCII, LF, parsed by powershell.exe 5.1
ParseFile in a test that is skipped off Windows) + `tests/test_ocr.py`.
Only files the plan 008 watcher listed are read, read-only, never the game.
Extractors (pure functions over OCR lines, tested on synthetic line lists):
silver amount (digits with commas near "Silver"), buff names matched against
the grind `SEED_BUFFS` with remaining minutes. `POST /api/ocr` `{"file":
name}` (name must be in the watcher list) -> `{text, silver?, buffs: [...]}`;
results cached per file in `ops/runtime/`. Nothing is applied automatically:
the dashboard offers "use this" which posts to `/api/grind` as normal input.

## Slice B - dashboard (lane `data`)

System tab screenshots card gains "Read" per file, a result panel and
"use silver" / "arm buff" buttons that go through the existing grind POSTs.

### Slice A deviations (adjudicated in-lane, 2026-10-05)

1. Reply shape is exactly `{text, silver, buffs}`; `silver` is always present
   (null when not found) rather than optional, and each buff is `{name,
   minutes}` with `minutes` null when no time was read. Alternatives: omit
   `silver` when absent; include `lines`/`file`. Why: one fixed shape is simpler
   for slice B and tests. Reverses if: slice B needs geometry (add `lines`).
2. OCR failure (engine missing, timeout, bad output) answers 502 `{"error":
   "ocr failed: ..."}`; an unlisted or malformed body answers 400 before any
   OCR runs. Alternatives: 400 for both. Why: 400 means the caller erred; a
   failing local engine is not the caller's fault. Reverses if: the shared POST
   guard is ever restricted to 400/200.
3. The cache stores the sanitised raw OCR `{text, lines}` per file under
   `ops/runtime/ocr/<sha256(name, size, mtime)[:32]>.json` (beside the store,
   so a test store keeps it in tmp), and the extractors re-run on every read.
   Failures are not cached; the cache is pruned to the newest 200 files (plain
   unlink - derived data, re-created by re-OCR). Alternatives: cache extracted
   results; key by name only. Why: an extractor fix needs no re-OCR; a
   re-saved file with the same name is re-read. Reverses if: OCR output needs
   per-version invalidation (add the extractor version to the key).
4. Durations: unit-tagged numbers only (d/day, h/hr/hour, m/min/minute,
   s/sec/second), summed, rounded UP to whole minutes, capped at grind
   `MAX_BUFF_MINUTES`. Clock forms `12:34` are NOT read (mm:ss vs hh:mm is
   ambiguous). Reverses if: the operator check shows BDO buff tooltips use a
   clock form - then read it per the measured meaning.
5. Silver: the first comma- or dot-grouped (OCR spacing tolerated) or plain
   number after, else before, the word "Silver" on its line, else on the same
   row (nearest by x), else within two line heights below; values over grind
   `MAX_SILVER` are dropped. Buffs: word-bounded, case- and punctuation-
   insensitive match of `grind.SEED_BUFFS`, time from the rest of the line,
   else the same row, else just below; first sighting per name wins. Reverses
   if: operator screenshots show the silver figure elsewhere (data change only).
6. `tools/ocr.ps1` scales images over `OcrEngine.MaxImageDimension` down with a
   BitmapTransform and maps coordinates back to original pixels; stdout is pure
   ASCII (non-ASCII `\u`-escaped) so no console code page matters. One OCR runs
   at a time (service lock); timeout 60 s. Measured on this host with rendered
   test images (not committed, no game files): 900x300 black-on-white read
   `Silver 1,234,567` / `XP scroll 59 min` exactly; a 4000x2000 image (scaled)
   dropped the digits after "Silver" - the plan's accuracy reverse-trigger is
   to be checked on real operator screenshots.
   Refute round 1 (verifier, separate renders): `Silver 1,234,567` read as
   `Silver 1` in 3 renders (Arial 28, Segoe 24/36); `1.234.567`, `Silver: 98,765`
   and white-on-dark `12,345` read correctly; ~0.5 s per image. Comma-grouped
   silver is UNRELIABLE until measured on real screenshots (operator item).
   Also fixed in round 1: two buffs on one OCR line each get their own time;
   an unwritable cache no longer drops the reply.

### Slice B deviations (adjudicated in-lane, 2026-10-05)

- `validOcrBody` is stricter than the server: exactly `{file}`, a bare name of
  1-255 characters with no `/`, `\`, `:` or control characters, never `.` or
  `..`. Alternative: any string (server-only check). Why: the main-process IPC
  guard should refuse a path before it reaches the server.
- `normalizeOcr` drops junk buffs, rounds fractional minutes, clamps to the
  grind 30-day cap, keeps one row per name (case-insensitive), caps text at
  20000 characters, and accepts silver only as a whole number in the grind
  range. Why: every buff shown must pass `validGrindBody` when armed.
- "use silver" with no Grind session running (or the Grind tab not loaded yet)
  copies the plain digits to the clipboard. With a session it only pre-fills
  the stop form's silver field; nothing is posted until the operator presses
  "Stop + log". `EWGrind` gains `prefillSilver(text)` and `refresh()` (re-poll
  after "arm buff"). Alternative: the game card GETs `/api/grind` itself. Why:
  one owner of grind state; no duplicate poll.
- The OCR panel sits outside the 10 s polled body so a poll never resets the
  text scroll; one Read at a time (buttons disabled while busy).
- The plan 008 guard "game card never writes" in `app/test/game.test.js` is
  replaced: the card's only POSTs are bridge calls to `/api/ocr` and
  `/api/grind`, and it never uses a renderer fetch POST.
- A reply over the bridge's 64 KB read cap parses as no data and shows "bad
  reply from server"; text is capped server-side by slice A in practice.

### Follow-up: engine benchmark (adjudicated 2026-10-05, replaces the operator check)

Decision: Tesseract (5.4, UB Mannheim build, already installed on this host)
becomes the primary engine; Windows.Media.Ocr is the fallback when Tesseract is
absent or fails. Measured with `tools/ocr_bench.py` (288 synthetic renders:
"Silver N", bare "N", "Silver: N", N 4-12 digits comma-grouped, Arial / Segoe UI
/ Tahoma / Malgun Gothic at 11-28 px, light-on-dark and dark-on-light crops plus
1920x1080 dark frames with distractor UI text; scored exact by the production
extractor):

| config | pass | ms/img |
|---|---|---|
| Windows OCR as is | 105/288 | 17 |
| Windows OCR 2x upscale | 159/288 | 63 |
| Tesseract x1 psm6 / psm11 | 254 / 257 | 112 / 119 |
| Tesseract x3 psm6 / psm11 (gray, invert-if-dark) | 284 / 282 | 277 / 330 |
| production chain (x3 psm6 -> x3 psm11 -> x1 psm6, replayed) | 284/288 | - |

Windows OCR fails mostly by truncating at the first comma ("Silver 1"), the
verifier's finding, at every size. Tesseract's misses are a comma read as a
space ("1 234 567", "2,814 ,995"), so `AMOUNT` now accepts a single space or a
spaced separator between 3-digit groups (+22 psm6, +19 psm11 at x3 on rescoring). The 4
remaining misses are one wrong glyph each. Live end-to-end on the renders: ~0.7 s
per crop, ~1.8 s per 1920x1080 frame.

- Preprocessing `tools/ocr_prep.ps1` (System.Drawing: grayscale, invert when the
  sampled mean brightness < 0.5, bicubic upscale, longest side capped at 8000).
- `config/local.json` `ocr.engine` (auto | tesseract | windows) and optional
  `ocr.tesseract` path; else PATH, else `%ProgramFiles%\Tesseract-OCR`.
- Cache key gains `CACHE_VERSION` so Windows-OCR reads cached before the switch
  are re-read once.
- Alternatives: Windows OCR with 2x/3x upscale (55 percent, rejected); Tesseract
  psm11 first (2 fewer passes, rejected); both engines and vote (2x cost, no
  measured gain over the chain).
- Reverses if: the real-screenshot check (operator item, now optional QA) shows
  Tesseract worse than Windows OCR on >1 of 10 shots - set `ocr.engine` to
  `windows` (config only) and re-run the benchmark with real crops.
- Refute round 1 (verifier, fresh renders): Tesseract psm 6 joined a whole row,
  so "Silver 1,234,567" plus "100" / "120/192" / "150" elsewhere on the row read
  1234567100 etc. Fix: `parse_tsv` splits a line at a word gap wider than
  `GAP_SPLIT` (0.8) word heights; all three now read 1234567, bench unchanged
  (chain 284/288). (The one/two-space residual noted here was fixed
  2026-10-05, see "Word-gap fix" below.) Verifier also confirmed Windows OCR returned empty text
  on all six 12-16 px crops while Tesseract read every buff line.

## Word-gap fix (2026-10-05): "Silver 1,234,567  100" no longer reads 1234567100

Measured (Tesseract tsv at x3, gap / max word height, digit word to digit
word): a comma Tesseract dropped 0.12-0.55; one real space 0.32-0.58; two
0.59-1.00; three 0.85-1.42. One space overlaps a dropped comma by geometry and
by text; two do not.

1. `parse_tsv`: a digit|digit boundary splits the line when the gap is over
   `DIGIT_GAP_SPLIT` 0.57 h, or the word heights differ by over 20 percent,
   or their bottoms by over 0.25 h (another UI element). Other boundaries keep
   `GAP_SPLIT` 0.8.
2. One space: ink probe (`tools/ocr_ink.ps1`, one PowerShell call, only when
   the chosen silver amount spans a kept digit gap >= 0.25 h). A gap with no
   dark pixels (< 0.02) around the baseline is a real space and the amount is
   cut there; ink = a dropped comma, kept. Never cut before a grouped tail
   ("21 187,096,269" stays one number). Probe failure keeps the joined read.
   `CACHE_VERSION` 3.
3. Live chain on renders (this session): new "Silver 1,234,567 + 1/2/3
   spaces + 100" set (4 fonts x 5 sizes x crop/frame) 66/120 -> 120/120; old
   quick bench set 142/144 -> 141/144. The one loss (c0017, 13 px dark on
   light) is a comma Tesseract dropped whose pixels are gone after prep (0 ink
   at any threshold) - indistinguishable from a space by any signal we have.
- Decision (adjudicated in the main session): ship the probe. Alternatives:
  text-only rule "plain space after comma groups ends the number" (breaks 5
  of 144 real comma-drop reads); geometry only (fixes two spaces, not one);
  status quo. Why: +54 fixed vs -1 lost on renders, and BDO shows silver alone
  so a real neighbour number is rare either way. Reverses if: the real-
  screenshot QA shows a comma-drop cut on real crops - then raise the probe
  gap floor or drop step 2 (`PROBE_GAP`).
